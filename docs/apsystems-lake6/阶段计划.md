# Lake_6 阶段计划（M1–M6）

- 配套文档：`Lake6-开发基线.md`（设计契约）、`设备页与实体定位指南.md`（验收时怎么找实体）
- 本文档只回答三个问题：**分几个阶段、为什么这么切、每个阶段的完成标准是什么**
- 任何阶段的实操与 `Lake6-开发基线.md` 冲突，以基线文档为准

---

## 一、总览

| 阶段 | 做什么 | 产出文件 | 依赖谁 | 怎么验证 |
|---|---|---|---|---|
| **M1** | 定契约：端点 → 实体映射 + 架构决策 | `Lake6-开发基线.md` | 无 | 人评审（**已完成**） |
| **M2** | 协议层：拼 URL、校验 `code`、转类型 | `lake6/client.py`、`lake6/const.py` | M1 | `pytest`，喂真实 JSON，**不需要 HA** |
| **M3** | 数据层：定时拉取、缓存、失败降级 | `lake6/coordinator.py` | M2 | `pytest` + mock client，**不需要真实设备** |

| **M6** | 收尾：翻译 + 全量回归 | `strings.json`、`translations/en.json` | M4 / M5 | 全量 pytest + 快照零 diff |

## 二、为什么不能一口气写完

这就是分层的全部意义：**让 bug 在它能被定位的那一层停下。**

假设跳过 M2/M3，直接写 35 个实体。跑起来发现"电池电量显示 unknown"，可能的原因有 6 种：

1. client 没发请求
2. 请求发了但 URL 拼错
3. 设备返回 `code != 200` 但没抛异常
4. `"21.0"` 转 float 失败
5. coordinator 没把数据存进去
6. 实体的 `value_fn` 字段名写错（`soc` 写成 `battery_soc`）

**6 个怀疑对象散在 800 行代码里**，只能靠打日志一个个试。

分层之后：

| 阶段 | 能证明什么 | 代价 |
|---|---|---|
| M2 | 直接给 `Lake6Client` 喂真实 JSON，断言 `result.battery_soc == 21.0`，**证明 1–4 全对** | 不用启动 HA、不用连设备，单测 0.2 秒 |
| M3 | 塞假 client（固定返回 21.0），断言 `coordinator.data.energies.battery_soc == 21.0`，**证明 5 对** | 不需要真实设备 |
| M4 | 此时若仍 unknown，**只可能是 6**，看一眼 `value_fn` 即定位 | 快照可复现 |

后面每一层都把前面所有层当成**已验证的黑盒**。

## 三、每个阶段的完成标准

### M2 — `lake6/client.py`

- 5 个方法：`get_device` / `get_energies` / `get_alarms` / `get_modes` / `set_modes`
- 用实测的 4 段真实 JSON 作测试数据，**逐字段断言**
- 6 个错误码（1001 / 1002 / 1003 / 1004 / 2001 / 未知码）逐个断言抛 `Lake6ApiError`
- `rssi` 传 `-43`（int）与 `"-43"`（str）都必须成功
- 某字段传 `""` 时该字段为 `None`，其它字段不受影响
- **验收**：`pytest tests/components/apsystems/lake6/test_client.py` 全绿，全程不 import `homeassistant.core`

### M3 — `lake6/coordinator.py`

- `Lake6Coordinator` + `Lake6Data` + `Lake6RuntimeData`
- 三级节流：`/energies` 每次拉、`/alarms` 60 秒、`/modes` 300 秒
- 写操作后置脏标记，强制下次拉 `/modes`
- client 抛异常 → `UpdateFailed`；首次失败 → `ConfigEntryNotReady`
- **验收**：用 mock client 断言"12 秒内 `alarms` 只被调用 0 次（尚未到 60 秒）"

### M4 — 35 个实体

- 5 个 Lake 平台文件 + 4 个现有平台文件的 `isinstance` 分支
- 每个实体 `unique_id = f"{device_id}_{key}"`
- **验收**：4 份 `.ambr` 快照，其中 **EZ1 的 4 份必须零 diff**

### M5 — 添加设备流程

- 表单加 `device_type`（`ez1` / `lake6`），端口默认值跟随类型
- 用 `get_device()` 拿 `dev_id` 做 `unique_id`
- 老条目 `device_type` 缺省为 `ez1`，`VERSION` 不变、不写 migration
- **验收**：同型号同 IP 无法重复添加；老 EZ1 条目重载后一切不变

### M6 — 收尾

- `strings.json` 补全 35 个实体 key + 2 组 `state` 映射（`battery_status` / `operating_mode`）+ 异常文案
- 生成 `translations/en.json`（自定义集成路线必须提交，否则实体名显示裸 key）
- **验收**：全量 pytest + `ruff check` + `mypy` strict 全过

> **实操建议**：`strings.json` 不要真的留到 M6 才写。M4 写完每个平台时随手补上对应 key，M6 只做"生成 en.json + 校验 key 与代码一一对齐"。文档把 M6 单列，是当作一道**收口检查**，不是"前五个阶段都不管翻译"。

## 四、依赖关系

```
M1 契约
  └→ M2 client ──────────┐
       └→ M3 coordinator │
            └→ M4 实体   │
                 └→ M6 翻译/回归
       └→ M5 config_flow ┘
```

- **M6 必须最后**：要跑全量回归，前面的东西不全就没得跑。
- **M3 必须在 M2 后**：coordinator 只是"按频率调用 client 的方法"，client 没写完就无从调用。
- **M4 必须在 M3 后**：实体的 `value_fn` 直接读 `coordinator.data.xxx`，这个数据形状是 M3 定的。
- **M5 可以早于 M4**：`config_flow` 只需要 M2 的 `get_device()`，不依赖实体。排在 M4 后只是因为它用 `MockConfigEntry` 测试，写法在 M4 的快照测试里已有现成范例。**若想先能"添加设备"，把 M5 提到 M4 前面完全可行**，不违反任何决策。

## 五、与待确认项的关系

`Lake6-开发基线.md` §12 的 C1–C9 不阻塞 M2 开工：

| 待确认项 | 阻塞哪个阶段 | 确认前的默认行为 |
|---|---|---|
| C1 `power_limit` 缺失原因 | 不阻塞 | 缺失即 `None`（unknown） |
| C2 AI 提示文案 | 不阻塞 | `strings.json` 放占位文案 |
| C3 `bat_cap` 单位 | 不阻塞 | 按 kWh |
| C4 `bat_power` 符号方向 | 仅影响 M4 的统计语义 | 原值输出 + TODO |
| C5 AI 切换是否生效 | 不阻塞 | 视为生效 |
| C6 累计量归零 | 不阻塞 | `TOTAL_INCREASING` 自动处理 |
| C7 错误码语义 | 不阻塞 | 按 §9 默认行为 |
| C8 `bat_manuf` / `bat_model` 含义 | 不阻塞 | 不消费 |
| C9 `backup_charP` 范围 | 不阻塞 | 0–2500 |

**结论：可以立即开始 M2。**
