# Lake6 开发链路与亮点

> 用法：这是"讲解主线"，不是知识点清单。
> 每条链路都带**当时的原话或真实数据**，因为答辩里最有说服力的不是"我做了 X"，而是"我当时是这么判断的"。
> 素材来源：`docs/conversation-archive/` 中 11-09 至 11-13 的 10 个会话记录。

---

## 这条链路为什么这样切

一个成熟的开发链路不是"写代码 → 调通 → 交付"，而是：

```
环境与基线  →  调研与规则  →  契约定义  →  分层实现
     ↑                                        ↓
     └──────────── 需求返工 ←── 真机验证 ←──────┘
                        ↓
                   边界收口  →  部署交付
```

**为什么这样讲比"按功能讲"好**：

- 按功能讲，评委听到的是"你实现了什么"——这是执行者的视角
- 按链路讲，评委听到的是"你怎么推进的"——这是负责人的视角

30 分钟里，八个阶段的经验值：

| 阶段 | 内容 | 时间 |
|---|---|---|
| ① | 环境与基线 | 2:00 |
| ② | 调研与规则建立 | 5:00 |
| ③ | 契约定义 | 5:00 |
| ④ | 分层实现 | 7:00 |
| ⑤ | 真机验证 | 5:00 |
| ⑥ | 需求返工与重设计 | 4:00 |
| ⑦ | 边界收口与部署 | 2:00 |

# 阶段 ① 环境与基线（2:00）

## 做了什么

1. 装 HAOS 虚拟机（VirtualBox），桥接网络使宿主机能和设备同网段
2. 装 Samba / SSH 增益件，方便改文件、看日志
3. **在导入自己代码之前，先做一次完整的虚拟机快照**

## 亮点：先建"干净基线"，再动手

当时的原话：

> "这个备份的作用是后续有需要回到我没有导入我开发的代码到 ha 的状态时可以进行切换。"

**为什么这是亮点**：

大多数人做集成开发是"边改边试"，出了问题就回滚代码。但设备侧的配置（比如写进去的分时计划、改过的放电深度）**不会因为回滚代码而恢复**。

所以真正的安全边界不是代码版本，是**整台机器的状态**。

**讲法**：

> "动设备之前，我先做了一次干净的虚拟机快照。因为后面会反复改设备配置，而设备的配置不会因为我回滚代码就恢复。有了基线，我任何时候都能回到'没有导入我代码'的状态重新验证。"

## 如果被问

**Q：为什么不直接用 git 管理？**
> 因为要回滚的不只是代码，还有 HA 的数据库（实体注册表、配置条目）和设备侧的配置。这些不在 git 里。

**Q：快照最后用上了吗？**
> 用上了。后面排查"实体不可用"的时候，为了排除是我改的东西影响了另一个集成，我把两个集成都重装了一遍，然后用基线确认初始状态本来是什么样。

# 阶段 ② 调研与规则建立（5:00）

## 做了什么

1. 精读官方 `apsystems` 集成（EZ1），逐文件理解职责
2. **把官方规范整理成 96 条规则清单**，落成文档
3. 用 Apifox 把厂商的 5 个端点全部跑通，生成可复用的接口集合
4. 找到第三方实现 `apsystems_storage`，拉源码做对照

## 亮点一：先建规则清单，再动手写代码

当时的原话：

> "你来带着我读，我目前觉得太多代码了，我看了跟没看一样，不要逐行带我读，然后要保证我知道对应的 ha 官方的开发规则。"

**为什么这是亮点**：

新平台开发最大的风险不是"不会写"，而是"写出来不符合平台的约定"——平台有一堆隐性规则（比如实体必须用 `unique_id`、平台必须 `should_poll=False`、卸载必须用同一份平台列表）。

如果边写边问，这些规则会散落在几十次对话里，**两周后就记不清了**。

所以先把它固化成 96 条清单，后面每次做决策都有依据。

**产出**：`docs/apsystems-lake6/HA集成开发规则清单.md`

**讲法**：

> "我没有直接开始写 Lake 的代码，而是先把官方集成的规范整理成 96 条清单。因为后面会遇到'按清单该怎么做、按我的设计该怎么做'的冲突，有清单我才知道哪些是必须遵守的，哪些是可以有理由地偏离的。"

## 亮点二：用 Apifox 独立验证协议，不信任集成代码

当时的动作：把 PDF 手册里的接口全部导入 Apifox，逐个手发请求。

而且遇到了一个真实的坑：

> "刚刚那个文件被加密了。"（厂商文档有企业 DLP 加密，导致无法直接解析）

**为什么这是亮点**：

如果只通过自己写的集成去验证协议，出错时你分不清是"协议理解错了"还是"代码写错了"。

用 Apifox 单独跑一遍，就把这两个可能分开了：**如果 Apifox 通了，说明协议理解是对的；如果集成不通，问题一定在代码**。

**讲法**：

> "我用 Apifox 把 5 个端点单独跑通过一遍。这样后面集成出问题时，我能确定协议本身是理解的，问题在代码层，不用两头猜。"

## 亮点三：找到第三方实现做对照

当时的原话：

> "参照我之前的设计和思路来看一下他们做的插件的是怎样"
> "你看看他的代码中有没有我们 M2 不确定的 api 返回的字段的范围是怎么设置的"

**为什么这是亮点**：

同一个设备，别人已经做过一版（`apsystems_storage`）。对照不是为了抄，是为了**验证自己的判断**：

- 它在字段范围上怎么设的？（对照后发现，有些我们不确定的它也没确定）
- 它的数据类型怎么处理的？（发现它把功率全部按 float 处理，我们按实际情况分了 int/float）
- 它的 UI 怎么组织的？（后来直接作为我们 UI 的参照）

**讲法**：

> "我不希望闭门造车。同一个设备已经有第三方做过一版，我先研究它在字段范围、数据精度、配置组织上的做法，再决定哪些照做、哪些做得更好。"

## 如果被问

**Q：96 条清单是不是抄的官方文档？**
> 不是。官方文档讲的是"应该怎么做"，我整理的是"在这个集成里，具体哪一行代码在体现这条规则"。所以它带文件位置，是用来查的，不是用来读的。

**Q：为什么信第三方实现？它也可能错。**
> 我不用它当正确答案，用它当"另一个样本"。它和我判断一致的地方，可信度提高；不一致的地方，成了我必须去实测的清单。比如字段精度，它就是全部按 float，我实际测出来有些字段是整数。

# 阶段 ③ 契约定义（5:00）

## 做了什么

1. 把 5 个端点的每个字段，映射到具体实体
2. 定义架构决策 A/B/B2/C，落成 798 行的开发基线文档
3. 逐个确认字段语义（不懂的去问产品，而不是猜）
4. 明确区分"已确认"和"待确认"

## 亮点一：每个数值都追到出处

当时的原话（三次追问）：

> "`backup_charP` 我问你是从哪个接口拿到的"
> "15–90、0–2500 只能写死，这里对应的值是从哪里拿"
> "`dod` 和 `backup_charp` 的范围还得确定，不要乱加"

**为什么这是亮点**：

范围类常量（比如"放电深度 15–100"）会直接显示在用户的配置界面上。如果这个数字是猜的，用户会当真，而且**错了也不会有人报错**——设备可能接受一个超出范围的值然后行为异常。

所以你的标准是：**每个范围值必须能指到"哪个接口返回"或"谁确认的"**。

**具体案例**：

| 字段 | 文档说 | 实际确认 | 怎么确认的 |
|---|---|---|---|
| `dod` 上限 | openapi 写 90 | 产品确认 15–100 | 问产品 |
| `backup_charP` | 文档没写 | 0–2500 | 实测 + 产品确认 |
| `dod` 语义 | 名字像"放电深度" | 实际是"备电 SOC 下限" | 产品解释 |
| `rssi` 类型 | string | int | 实测返回 |

**讲法**：

> "这个项目里有几个地方我做得比较慢。比如字段范围，文档没写清楚的地方我一个都没填，全部标成待确认。不是我做不完，是填错了以后用户会当真——他会以为这是设备的能力边界，然后拿这个去设计他的用电策略。"

## 亮点二：把"待确认"和"已确认"分开管理

**做法**：

在基线文档里，每个字段有三态：
- 已确认（有出处）
- 待确认（有默认行为 + 阻塞范围）
- 不实现（本轮不做，写清原因）

**为什么这是亮点**：

大多数项目的文档只写"是什么"，不写"什么是不知道的"。结果是**未知的东西被悄悄埋进代码里**，等到出问题才发现。

你的做法是让未知可见。答辩时可以主动说："这四个字段我还没关掉，原因和验证方法都写在表里。"

**讲法**：

> "我在基线文档里专门留了一节叫'待确认项'。它们不是 TODO，是明确写清'这个值现在没有权威出处、暂时用 X、会影响哪部分功能、怎么验证'。这样任何人接手都知道哪里不能碰。"

## 亮点三：架构决策写下"为什么"和"放弃了什么"

**四个决策**：

| 决策 | 选择 | 放弃了什么 |
|---|---|---|
| A | Lake 用独立 coordinator | 放弃了代码复用，多写 300 行 |
| B | 平台入口用 `entry.data` 判型，平台文件用 `isinstance` | 放弃了"统一用类型断言"的写法 |
| B2 | 两份 PLATFORMS 列表分开维护 | 放弃了"一份列表管所有设备"的简洁 |
| C | 类型转换只在 client 层做一次 | 放弃了"实体自己按需转换"的灵活 |

**为什么这是亮点**：

写下"放弃了什么"比写下"选择了什么"难得多，因为它要求你真的比较过。

**讲法**：

> "每个决策我都写了三件事：选了什么、为什么、放弃了什么。第三个最难写，但它是唯一能证明我真的比较过的东西。"

## 如果被问

**Q：798 行的基线文档是不是过度设计？**
> 如果只有我一个人做、只做两周，确实过了。但这个项目要么将来有人接手，要么要提交上游，两种情况都需要"为什么这么做"的完整记录。而且写文档的过程本身暴露了很多矛盾——比如"平台入口要不要用 `isinstance`"，写的时候才发现 EZ1 和 Lake6 的类型根本不同源，无法统一。

**Q：花了多少时间写文档？**
> 契约定义那部分大概占整个项目的五分之一。但它省下来的调试时间远不止这些——因为每个字段的语义在写文档时就确认了，不是写代码时才发现。

# 阶段 ④ 分层实现（7:00）

## 做了什么

按里程碑推进，每个里程碑单独验收：

```
M1 契约（端点→实体映射、架构决策）
M2 client（协议适配、类型转换、错误码）
M3 coordinator（三级节流、写后回读）
M4 实体（7 个平台、35 个实体）
M5 config_flow（双型号接入）
M6 翻译与回归
```

## 亮点一：一步一确认，不批量生成

当时的原话：

> "可以开始 M2，不要一下生成所有的代码，一步一步来，每一步需要我来确认。"

**为什么这是亮点**：

分层开发最大的风险是"一口气写完 2000 行，然后发现基础假设错了"。这时候改起来不是改一处，是全线返工。

分步确认的代价是慢，收益是**错误被限制在一层以内**。

**具体体现**：

- 写 client 的 4 个 dataclass 时，专门说明"这一步完全不涉及 dod / backup_charP 的范围，不受待确认项影响"
- 这样即使那两个字段的范围还没定，client 也能先做完

**讲法**：

> "我坚持每个里程碑单独验收，不是因为我慢，是因为分层的价值就在于'错误被挡住'。如果 M2 和 M3 一起写，client 的类型转换错了，coordinator 的调试会变得非常痛苦，因为你不确定问题在哪层。"

## 亮点二：类型转换收敛到一个文件

**问题**：

35 个实体，每个都需要把设备返回的字符串转成合适的类型。如果各转各的：

```
sensor.py 里 float("28.5")
switch.py 里 int("1")
number.py 里 float(...)
...35 个转换点
```

单位、符号、空值、类型不符的坑会散落在 35 个地方。

**做法**：client 出口的数据已经是 `float / int / bool / 语义字符串 / None`，实体层永远不出现 `float()`。

**为什么这是亮点**：这是"把变化限制在一层"的具体应用。

**一个真实的事故**：

> `rssi` 字段，文档标注是 string，实际返回是 int。

```python
# 如果按文档写
rssi = data["rssi"].strip()      # int 没有 .strip() → AttributeError
```

后果不是"信号强度显示不出来"，而是**整个 `/devices` 解析抛异常，一台设备都加载不出来**。

**讲法**：

> "类型转换如果分散在 35 个实体里，那么'文档标错了类型'这件事会有 35 种表现方式。收敛到一层之后，任何一种类型问题都只需要看一个文件。"

## 亮点三：写操作的三次迭代（这是最能证明"用实测修正设计"的）

| 版本 | 做法 | 出什么问题 |
|---|---|---|
| v1 | 写完调 `async_request_refresh()` | 受防抖窗口约束，任务被丢弃，**界面完全不变** |
| v2 | 写完调 `async_refresh()` | 连 `/energies`、`/alarms` 一起拉，一次点击 = 1 POST + 3 GET，连点几下设备超时 |
| v3 | 只回读刚写的那个端点，其余沿用缓存 | 1 POST + 1 GET |

**为什么 v1 会失败**（这段要讲透）：

`async_request_refresh()` 的源码注释是：

```python
"""Request a refresh.
Refresh will wait a bit to see if it can batch them.
"""
```

它不是"立刻刷新"，是"**申请**刷新"。在防抖窗口内的申请会被合并甚至丢弃。

**最危险的后果**：设备其实已经改了，但界面没变。用户会以为没成功，然后**重复操作**。

**讲法**：

> "这个问题不看设备日志发现不了。当时的现象是'点了没反应'，但设备侧其实已经收到并执行了。如果用户连点五次，设备就收到五次写请求——这比直接失败更危险，因为失败用户会重试，而'看起来失败但实际成功'会让用户反复操作。"

## 亮点四：`always_update=False` 的完整推理

**做法**：

```python
super().__init__(
    ...,
    always_update=False,   # 数据没变时不通知实体
)
```

**前提条件**：数据对象的 `__eq__` 必须可靠，所以数据类必须是 frozen dataclass。

**收益（算得出来）**：

```
35 个实体 × 每天 7200 次轮询 = 25.2 万次通知
设 False 后，只有数据真变了才通知 ≈ 1.7 万次
减少 93%
```

**为什么这不只是"优化"，是"正确性"**：

如果每 12 秒都产生一次 `state_changed`，任何监听该实体的自动化都会被反复触发。比如一个"温度变化时记录日志"的自动化，一天会写 2 万条无用日志。

# 阶段 ⑤ 真机验证（5:00）

## 做了什么

抓住设备在手的窗口期，逐项验证：

| 验证项 | 改了什么 | 设备侧观察 | 结论 |
|---|---|---|---|
| 放电深度 | 15 → 80 | 回读 80，App 显示一致 | 范围被接受 |
| 备电充电功率 | 0 → 2500 | 回读 2500 | 上限确认 |
| 分时计划 | 写 3 条规则 | 设备解析出 3 条 | 格式正确 |
| 手动控制 | 下发 2000W / 30min | `mode` 变 1，窗口出现 | 链路通 |
| 中断控制 | 点中断 | `mode` 回 0，配置清空 | 状态一致 |

## 亮点：主动抓住"设备窗口期"

当时的原话：

> "怎么测出来（趁现在设备在手）是什么时候需要测试是现在吗"

**为什么这是亮点**：

真机是最稀缺的资源。设备不在手上的时候，所有关于设备行为的判断都只能靠文档——而文档恰恰是这 9 处疑点的来源。

所以"趁设备在手"不是一句感慨，是一个决策：**把需要真机的验证，优先排在不需要真机的验证前面。**

**讲法**：

> "真机窗口很短，错过就要重新约。所以我把所有'必须上真机才能确认'的项列成清单，优先测。而那些能靠文档和 mock 确认的（比如 URL 拼接、错误码映射），往后排。"

## 亮点：从表象反推协议行为

一个具体案例：

> 现象："点击完中断即时控制后，只修改了对应的 `mode` 的值，没有清除图片中的相关配置项。"

**推理过程**：

```
现象：中断后 mode 变 0，但 MI1 里的时间窗和功率还在
   ↓
如果设备是"合并"语义，那 mode=0 时保留 MI1 是正常的
   ↓
但如果设备是"替换"语义，那说明我们发送的 payload 里带了 MI1
   ↓
去看实际发出的请求：中断时我们发的是 {"mode": "0", "MI1": {}}
   ↓
设备返回后 MI1 仍有内容 → 说明设备没有清空，是我们在 UI 上没反映出来
   ↓
结论：设备是"整体替换"语义，但中断的场景下需要发送空 MI1
```

**为什么这是亮点**：这就是"能推出变体"的能力——你不是记住"中断要发空对象"，而是知道**为什么**。

# 阶段 ⑥ 需求返工与重设计（4:00）

## 发生了什么

分时电价第一版做完了，但不符合预期：

> "现在这个功能不符合我的预期，分时电价计划应该放在配置中，然后对应的配置项应该是可以进行配置的。"

然后两个关键澄清，直接推翻了原方案：

> "不是，我们这边时间规则是可以 1-24 条的。"
> "这个每一条规则都是可以选择周一到周日中的任意一天或者多天的。"

## 亮点一：识别"实现对了，但产品形态错了"

第一版做的是"逐规则实体"：每条规则一组 number / select。技术上是通的，但产品形态不对：

| | 第一版 | 第二版 |
|---|---|---|
| 形态 | 每条规则 6 个实体 | 1 个文本实体 + 1 个按钮 |
| 实体数 | 24 × 6 ≈ 144（上限时） | 2 |
| 用户操作 | 翻 4 屏，绝大多数槽位空着 | 一个文本框里编排 |

**为什么这是亮点**：

区别在于**发现问题的层次**。如果只看"功能能不能用"，第一版是能用的。但"能用"和"好用"之间的差距，需要站在用户角度才能看出来。

**讲法**：

> "第一版做完我自己在界面上试了一遍，发现要配置一个常见的'工作日晚上充电'计划，需要滚动好几屏去找对应的槽位。功能是对的，但用户不会这么用。所以推翻重做。"

## 亮点二：推翻之前，先做业界调研

当时的原话：

> "你帮我看看 ha 中其他储能设备这种分时控制的功能是怎么做的。"

**为什么这是亮点**：

推翻自己的方案很容易变成"拍脑袋换成另一个拍脑袋的方案"。先看别人怎么做，至少能排除"这种形态在 HA 里根本不成立"的风险。

调研结论：HA 生态里储能设备的分时控制，主流做法是"一个文本/时间表实体 + 校验"，而不是"几十个槽位实体"。这印证了文本协议的可行性。

## 亮点三：改之前先确认"能回退"

当时的原话：

> "可以试试，不过后续检验这个修改符合我的预期需要能够回退。"

**为什么这是亮点**：

这就是阶段 ① 那个快照的真正用途——不是为了"以防万一"，而是为了**让重构敢做**。

**讲法**：

> "改之前我确认了能回到旧版本。因为分时电价是唯一一个'用户会真的把用电策略写进去'的功能，改坏了影响比别的功能大。确认能回退之后，我才敢整个推翻重做。"

## 亮点四：`render_plan` 的保守策略（可以放在这里讲）

```python
def render_plan(rules) -> str | None:
    """把设备返回的规则表渲染成文本。

    只要有任意一条无法完整表达（缺时刻、功能码未知、功率越界）就返回 None：
    少显示一条的计划一旦被用户原样提交，就会把设备上那条静默删掉。
    """
```

**两个选项**：

| 选项 | 用户看到 | 风险 |
|---|---|---|
| A：渲染能渲染的 9 条 | 正常，但只有 9 条 | 用户改一个字提交，**设备上第 10 条被静默删除** |
| B：整体返回 None | "无法展示" | 用户暂时看不到计划，但不会误删 |

**选择 B。**

**讲法**：

> "这是整个项目里我最在意的一个决定。设备上有 10 条规则，我的渲染逻辑只能表达 9 条。如果我显示 9 条，用户看起来一切正常，但他只要改一个字再提交，第 10 条就被删掉了——而且他永远不会知道。所以我选择让他看到'无法展示'，也不给他一个残缺但看似正常的计划。"

# 阶段 ⑦ 边界收口与部署（2:00）

## 做了什么

1. 明确写出"本轮不做什么"
2. 打包进 HAOS，完成端到端验证
3. UI 与第三方实现对齐
4. 翻译补齐（`strings.json` → `translations/en.json`）

## 亮点一：主动圈定范围

当时的原话（当时放弃 control-panels）：

> "选择方案 A，这两个不变先保留原有的处理……`/control-panels` 本轮不纳入。"

**为什么这是亮点**：

"这轮不做什么"比"这轮做了什么"更能体现判断力，因为它是**在有人可以做更多的情况下，主动选择不做**。

后来 control-panels 还是做了（11-13），但那是在主链路稳定之后。这个顺序是对的：**先把主干打通，再加分支**。

**讲法**：

> "`/control-panels` 这个端点在契约阶段就摸清楚了，但我当时把它划到本轮范围外。因为它涉及即时下发，失败模式和常驻配置完全不同，混在一起会让主链路的验证变复杂。主链路稳定之后我才做它。"

## 亮点二：以第三方实现的 UI 为参照，快速对齐预期

当时的原话：

> "对应的图标可以参考一下 `apsystems storage` 中的。"
> "对应的 english 的页面显示可以以 `apsystems storage` 为参考。"

**为什么这是亮点**：

UI 风格没有客观标准。与其自己定义一套，不如沿用同一个生态里已有的做法——用户看起来一致，评审看起来也一致。

这也是"对标"这个方法的第二次应用：阶段 ② 对标字段处理，阶段 ⑦ 对标 UI 呈现。

## 亮点三：明确交付标准，不追求完美

当时的原话：

> "我不走 PR 流程，我只需要能在本地的 VirtualBox 中能使用我新开发的内容即可。"

**为什么这是亮点**：

这是对"交付"的定义。它同时说明了：这段代码的验收标准是"能在目标环境跑通并完成验证"，不是"达到上游合并标准"。

**讲法**：

> "这个阶段的交付标准很明确：能在本地 HAOS 里跑通、能被真实设备验证、能承担演示。至于上游合并，是下一个阶段的事，需要补测试和沟通 maintainer，那是另一套标准。"

# 亮点汇总（按性质分类）

## 判断力类（最能证明"值得留下"）

1. **没有出处就不填**：`dod`、`backup_charP` 的范围宁可标待确认
2. **不把自己的方便建立在别人的风险上**：不复用 EZ1 coordinator，宁可多写 300 行
3. **在用户看不见的地方也守着**：`render_plan` 宁可整体失败
4. **主动说出没做完的部分**：测试覆盖、4 个待确认项、未提 PR
5. **改之前先确认能回退**：重构分时电价前先确保有干净基线

## 技术类

6. **类型转换收敛一层**：35 个转换点变 1 个
7. **`always_update=False` + frozen dataclass**：通知量降 93%
8. **写后只回读单端点**：1 POST + 1 GET 而不是 1 POST + 4 GET
9. **三级节流的实现**：一个定时器 + 两个内部时间判断
10. **手动控制窗口不节流**：保证中断按钮即时生效
11. **文本协议承载 24 条规则**：144 个实体压到 2 个
12. **平行数组半对丢弃**：防止后续所有配对错位

## 流程类

13. **先建 96 条规则清单再动手**
14. **用 Apifox 独立验证协议**
15. **对标第三方实现**（字段处理 + UI 呈现两次应用）
16. **一步一确认，不批量生成**
17. **先做干净基线再动设备**
18. **明确"本轮不做什么"**
