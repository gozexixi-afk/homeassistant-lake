# Lake_6 设备页与实体定位指南

- 用途：从"设备返回的 JSON 字段"一路定位到"HA 界面上的哪一行"，供开发自测与 M4 验收使用
- 配套文档：`Lake6-开发基线.md`（设计契约）、`阶段计划.md`（M1–M6 里程碑）
- 基准设备：`D09001000127`（`http://192.168.1.139:80`），实体总数 38 个

---

## 一、先分清四个 ID（混了就无法定位）

| 名称 | 例子 | 谁生成 | 能不能改 | 用在哪个界面 |
|---|---|---|---|---|
| 设备注册表 ID | `3f9a...`（32 位十六进制） | HA 自动 | 不能 | 设备页 URL：`/config/devices/device/3f9a...` |
| 设备唯一标识 `identifiers` | `("apsystems", "D09001000127")` | 代码用 `DeviceInfo` 声明 | 不能（改了等于换设备） | 不可见，仅内部用于"这台设备是谁" |
| 实体 `unique_id` | `D09001000127_device_temperature` | 代码里 `f"{device_id}_{key}"` | **绝对不能** | 实体详情页的"唯一 ID"字段 |
| 实体 `entity_id` | `sensor.solar_device_temperature` | **HA 自动生成** | 用户可改 | 界面、自动化、仪表盘都引用它 |

**一条判断规则**：
- 报错/日志里出现 `D09001000127_xxx` → 那是 `unique_id`，去代码里搜 `key="xxx"`。
- 界面/自动化里出现 `sensor.xxx` → 那是 `entity_id`，去「开发者工具 → 状态」里搜。

## 二、实体是什么

一句话：**实体 = HA 里一个"有当前值、能被读写"的最小单位，界面上表现为一行或一张卡片。**

### 2.1 层级关系

```
集成 apsystems           ← 一个插件（代码包）
 └ 配置条目 ConfigEntry   ← 用户添加的一次记录（一台设备 + IP/端口）
    └ 设备 Device         ← 一台真实机器，由 DeviceInfo 定义（型号/序列号/固件）
       └ 实体 Entity ×38   ← 这台机器上的 38 个可读/可写项
```

**类比**：设备是"一辆车"，实体是"车速表、油量表、电量表、大灯开关、空调温度旋钮"。
车是一台，表有几十个。仪表盘上每一个表/旋钮，都是一个实体。

### 2.2 实体在代码里长什么样

```python
class ApSystemsSensorWithDescription(...):                # 一个类
    _attr_unique_id = "D09001000127_device_temperature"    # 全局唯一，永不改
    # 运行时 HA 自动生成 entity_id = "sensor.solar_device_temperature"
    # 当前值 state = 27.4
    # 属性：单位 °C、device_class = TEMPERATURE、entity_category = DIAGNOSTIC
```

### 2.3 实体和 `entity_category` 的关系

`entity_category` 是实体上的一个属性，**只决定它在设备详情页里的显眼程度**，不影响功能。

| 值 | 含义 | 设备页表现 |
|---|---|---|
| `None`（默认） | 主数据 | 平铺显示，页面主体 |
| `EntityCategory.DIAGNOSTIC` | 诊断数据 | 收进"诊断（Diagnostic）"折叠区 |
| `EntityCategory.CONFIG` | 集成自身配置 | 归入"配置"区块 |

### 2.4 图标从哪来

行首的小图标与 `entity_category` 无关，它按下面的顺序取：

1. 实体自己声明的 `icon`（`_attr_icon` 或实体描述子里的 `icon=`）
2. 集成根目录 `icons.json` 里按 `translation_key` 登记的默认图标
3. `device_class` 的内置默认图标（如 ENERGY 是闪电、POWER 是闪电）

Lake6 的 38 个实体全部走第 2 条：`homeassistant/components/apsystems/icons.json` 按平台 + `translation_key` 登记，图标取值参照 apsystems_storage 的同名字段（如 `battery_charge_energy` → `mdi:battery-arrow-up-outline`）。EZ1 的 key 一条也没写，所以 EZ1 界面图标保持原样。

> 改完 `icons.json` 后需要重载集成或重启核心，并强制刷新浏览器（Ctrl+F5），否则前端会用缓存里的旧图标。

### 2.5 英文显示名从哪来

英文界面上的实体名来自 `translations/en.json` 的 `entity.<platform>.<translation_key>.name`。`strings.json` 是开发期源文件，运行时只读 `en.json`，两份必须同步改。

Lake6 的 38 个名字统一参照 apsystems_storage 的写法：**每个实词首字母大写**，并尽量沿用它的措辞。

| 我们的 key | 英文显示名 | apsystems_storage 对应 |
|---|---|---|
| `battery_soc` | Battery SOC | Battery SOC |
| `grid_power` | On-grid Power | On-grid Power |
| `grid_export_energy` | On-grid Accumulated Output Energy | On-grid Accumulated Output Energy |
| `battery_over_voltage` | Battery Overvoltage | Battery Overvoltage |
| `offgrid_short_circuit` | Off-grid Short Circuit | Off-grid Short Circuit |
| `eco_mode` | Eco Mode | Eco Mode |
| `operating_mode` | Operating Mode | Operating Mode |

两处**不照抄**：

- `depth_of_discharge` 仍叫 **Backup SOC**。设备的 `dod` 字段存的是「备电保留的 SOC 下限」，而 Depth of Discharge 的常规含义是 `100% - SOC`，照抄会让数值含义反向（基线 §5.4）。
- `offgrid_output_enabled` 叫 **Off-grid Output**。apsystems_storage 里对应位置的 `off_grid_on_hold` 是「暂停离网」，语义相反，只借用了它的命名格式。

EZ1 的 15 个名字（sentence case，如 `Total power`、`Inverter status`）本次一行未动，英文界面仍是原样。

> 改名不影响已注册的 `entity_id`，但界面上看不到变化时要 Ctrl+F5 强制刷新。

## 三、设备页在哪

### 3.1 点击路径

```
左侧边栏「设置 (Settings)」
  └ 「设备与服务 (Devices & services)」
      ├ 顶部标签：集成 (Integrations) / 设备 (Devices) / 实体 (Entities)
      └ → 点「设备」→ 找到 Lake_6 → 点设备名
            ↓
         设备详情页：/config/devices/device/<设备注册表ID>
```

另一条路：`设置 → 设备与服务 → 集成 → 点 apsystems 卡片 → 点列表里的设备`。

## 四、38 个实体分别落在哪一块

### 4.1 主数据区（12 个，`entity_category = None`）

| 平台 | 数量 | 实体 |
|---|---|---|
| sensor | 12 | `battery_soc`、`battery_temperature`、`battery_status`（ENUM）、`battery_power`、`grid_power`、`offgrid_power`、`battery_charge_energy`、`battery_discharge_energy`、`grid_import_energy`、`grid_export_energy`、`offgrid_import_energy`、`offgrid_export_energy` |

> 全设备 sensor 共 16 个：此处 12 个主数据 + 下方 4.3 的 3 个诊断 + 1 个 `tou_schedule_format`（`CONFIG`）。

### 4.2 配置区（9 个，`entity_category = EntityCategory.CONFIG`）

| 平台 | 数量 | 实体 |
|---|---|---|
| number | 3 | `depth_of_discharge`、`manual_control_power`、`manual_control_duration` |
| select | 2 | `operating_mode`、`manual_control_mode` |
| switch | 2 | `eco_mode`、`offgrid_output_enabled` |
| text | 1 | `tou_plan` |
| sensor | 1 | `tou_schedule_format`（分时计划的格式提示，只读） |

> 这些实体都是**可写参数或配置文本**而非实时测量：设为 `None` 会混进主数据区，设为 `DIAGNOSTIC` 会被当成故障信息折叠，所以用 `CONFIG`。
>
> 注意 `depth_of_discharge` 就是产品的 `backupSoc`（备电放电 SOC 下限），**显示名必须用 “Backup SOC”**，不能写成 “Depth of Discharge”——后者的常规含义方向相反。
>
> `manual_control_mode` / `manual_control_power` / `manual_control_duration` 是 `/control-panels` 的**一次性手动控制**：三项都填好才会下发，改任一项就从当前时刻重新计时；待机（`standby`）恒下发功率 `0`，此时功率项不可用。

### 4.3 诊断区（17 个，`entity_category = DIAGNOSTIC`）

| 平台 | 数量 | 实体 |
|---|---|---|
| binary_sensor | 14 | `battery_over_temperature`、`battery_under_temperature`、`battery_communication_error`、`battery_over_voltage`、`battery_under_voltage`、`battery_over_current`、`battery_internal_error`、**`device_temperature_protection`**、`device_system_error`、`battery_shutdown`、`grid_anomaly`、`offgrid_over_current`、`offgrid_short_circuit`、`battery_calibration` |
| sensor | 3 | `device_temperature`、`battery_capacity`、`wifi_signal` |

### 4.4 合计核对

| 平台 | 总数 | 主数据 | 配置 | 诊断 |
|---|---|---|---|---|
| sensor | 16 | 12 | 1 | 3 |
| binary_sensor | 14 | 0 | 0 | 14 |
| number | 3 | 0 | 3 | 0 |
| select | 2 | 0 | 2 | 0 |
| switch | 2 | 0 | 2 | 0 |
| text | 1 | 0 | 1 | 0 |
| **合计** | **38** | **12** | **9** | **17** |

12 + 9 + 17 = 38，与基线文档 §5 的逐字段映射一致。

## 五、`entity_category` 影响范围（消除误解）

| 位置 | 受 `DIAGNOSTIC` 影响吗 |
|---|---|
| 设备详情页 | ✅ 被收进"诊断"折叠区 |
| 设置 → 设备与服务 → **实体** 列表页 | ❌ 所有 38 个平铺，不分组 |
| 仪表盘（用户自己拖的卡片） | ❌ 完全不受影响 |
| 自动化 / 脚本 | ❌ 完全不受影响，照常引用 |
| 历史记录 / 统计 | ❌ 完全不受影响 |

**结论**：标了诊断**不会**导致做自动化时找不到实体。

## 六、从 JSON 到屏幕的完整追踪链（以 `27.4` 为例）

### 6.1 六步定位

| 步 | 位置 | 看到什么 |
|---|---|---|
| 1 | `curl http://192.168.1.139/energies` | `"dev_temp": "27.4"` |
| 2 | `lake6/client.py` → `get_energies()` | 把 `"27.4"` 转成 `27.4`，存进 `Lake6Energies.device_temperature` |
| 3 | `lake6/coordinator.py` → `Lake6Data.energies` | 持有 `Lake6Energies` 对象 |
| 4 | `lake6/sensor.py` 描述表 | `key="device_temperature"`，`value_fn=lambda d: d.device_temperature` |
| 5 | 实体 | `unique_id = "D09001000127_device_temperature"` |
| 6 | 设备详情页 ③ 诊断区 | 卡片标题"设备温度"，状态 `27.4 °C` |

### 6.2 第 5 步到第 6 步之间：`entity_id` 怎么来的

因为 `_attr_has_entity_name = True`，实体显示名 = **设备名 + 实体名**：

```
config_flow 里 title="Solar"
  + strings.json 的 entity.sensor.device_temperature.name = "Device Temperature"
  → 显示名 "Solar Device Temperature"
  → entity_id "sensor.solar_device_temperature"
```

所以 entity_id 里既有设备名也有实体名，**不要靠猜，去「开发者工具 → 状态」搜**。

### 6.3 同名不同义陷阱（必须记住）

| 来源 | 原始值 | 含义 | 实体 | unique_id |
|---|---|---|---|---|
| `/energies` → `dev_temp` | `"27.4"` | 设备温度**数值**（°C） | `sensor.device_temperature` | `D09001000127_device_temperature` |
| `/alarms` → `dev_temp` | `"0"` | 设备温度保护**告警**（0=正常） | `binary_sensor.device_temperature_protection` | `D09001000127_device_temperature_protection` |

若把两个响应合并成一个 dict，后者的 `"0"` 会覆盖前者的 `"27.4"`，**温度永远显示 0 且不报错**（基线文档 §10 坑点 P2）。

## 七、自己核对的方法

### 7.1 查某个实体的准确 `entity_id` 与当前值

```
开发者工具 (Developer tools) → 状态 (States)
  → 搜索 "device_temperature" 或 "dev_temp"
```

能看到 `entity_id`、`state`、全部属性（单位、device_class、friendly_name）。

### 7.2 查实体挂在哪个设备、`unique_id` 是什么

```
设置 → 设备与服务 → 实体
  → 搜索实体名 → 点进去
```

实体详情页会显示：所属设备（可点击跳回设备页）、`unique_id`、`entity_id`、`entity_category`。

### 7.3 查设备页

```
设置 → 设备与服务 → 设备 → 点设备名
```

### 7.4 三个常见误判

| 现象 | 先查哪里 | 常见原因 |
|---|---|---|
| 设备页上找不到某个实体 | 设置 → 设备与服务 → **实体** 列表 | 实体被收进"诊断"折叠区，设备页默认收起 |
| 实体显示 unknown | 开发者工具 → 状态 | 该字段为 `None`（单字段容错生效），不代表集成故障 |
| 实体完全没创建 | 集成日志 + `unique_id` | 平台文件未 forward、或 `unique_id` 与已有实体冲突被丢弃 |

## 八、一句话总结

- **接口字段** 决定 **client 的数据类字段**，**数据类字段** 决定 **实体 `key`**，**`key`** 决定 **`unique_id`**，**`unique_id` + 设备名** 决定 **`entity_id`**，**`entity_id`** 出现在 **设备页的某个区块**。
- 定位任何一行界面文字，都从这条链的任一端往回搜即可。
